# Спецификация требований EARS: Billing Domain

## Группа 1: Базовые инварианты (Ubiquitous)
- [REQ-EARS-01] Система ДОЛЖНА валидировать баланс пользователя строго как целое неотрицательное число в копейках.
- [REQ-EARS-02] Система ДОЛЖНА возвращать все ответы в формате Pydantic v2 DTO с типизированными полями.
- [REQ-EARS-03] Система ДОЛЖНА изолировать логику базы данных за интерфейсом BillingRepositoryProtocol.

## Группа 2: Обработка событий (Event-driven)
- [REQ-EARS-04] КОГДА совершен переход по платной ссылке, система ДОЛЖНА инициировать транзакцию списания.
- [REQ-EARS-05] КОГДА передан уникальный transaction_id, система ДОЛЖНА проверить факт повторного запроса.
- [REQ-EARS-06] КОГДА поступает запрос на пополнение баланса, система ДОЛЖНА увеличить баланс кошелька.

## Группа 3: Поведение по состоянию (State-driven)
- [REQ-EARS-07] ПОКА тарифный план равен FREE, система ДОЛЖНА ограничивать число платных ссылок до 10.
- [REQ-EARS-08] ПОКА тарифный план равен ENTERPRISE, система ДОЛЖНА предоставлять нулевую комиссию за клик.
- [REQ-EARS-09] ПОКА транзакция находится в статусе PENDING, система ДОЛЖНА удерживать сумму на холде.

## Группа 4: Опциональные условия (Optional)
- [REQ-EARS-10] ЕСЛИ пользователь передал промокод, система ДОЛЖНА начислить бонусный баланс.
- [REQ-EARS-11] ЕСЛИ указан кастомный вебхук уведомления, система ДОЛЖНА отправить событие `billing.charged`.
- [REQ-EARS-12] ЕСЛИ запрошена выгрузка инвойса, система ДОЛЖНА сформировать сводный PDF-отчет.

## Группа 5: Обработка исключений и сбоев (Unwanted behavior)
- [REQ-EARS-13] ЕСЛИ средств на балансе недостаточно для списания, ТО система ДОЛЖНА вернуть статус HTTP 402 Payment Required.
- [REQ-EARS-14] ЕСЛИ передан дублирующий transaction_id, ТО система ДОЛЖНА вернуть сохраненный результат без повторного списания.
- [REQ-EARS-15] ЕСЛИ СУБД недоступна при списании, ТО система ДОЛЖНА откатить транзакцию и вернуть HTTP 503.
