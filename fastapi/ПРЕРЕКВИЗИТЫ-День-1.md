# 1. Системное окружение

## 1.1. Homebrew (только macOS)

Ставим менеджер пакетов macOS. Через него устанавливаются Docker Desktop, git и VS Code.

Пользователи Linux и Windows (WSL): шаги **1.1.1–1.1.4 пропустите**, git и окружение ставятся в шаге 1.2.4.

### 1.1.1. Установка Homebrew

```bash
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
```

Скачиваем и устанавливаем Homebrew. Сначала установщик выведет список создаваемых каталогов и строку `Press RETURN/ENTER to continue or any other key to abort` — нажмите клавишу **Enter**. Любая другая клавиша отменит установку. Затем установщик запросит пароль администратора Mac: вводите пароль разблокировки компьютера (символы при вводе в терминале скрыты — это штатное поведение).

**Ожидай:** в конце строку `Installation successful!` или `already installed`. Если терминал вернул приглашение без `Installation successful!` — была нажата не та клавиша, повторите команду. При таймауте сети (`curl: (7)`) включите VPN и повторите.

### 1.1.2. Apple Silicon — brew в PATH

Выполняется только на компьютерах Mac с чипами Apple Silicon (M1/M2/M3/M4). Пользователи Intel Mac переходят сразу к 1.1.3. Если сомневаетесь в типе процессора, выполните `uname -m`: вывод `arm64` означает чип Apple Silicon, `x86_64` — Intel.

```bash
echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile
```

Прописываем запуск окружения Homebrew в автозагрузку профиля zsh.

**Ожидай:** пустой вывод.

```bash
eval "$(/opt/homebrew/bin/brew shellenv)"
```

Активируем Homebrew в текущем окне терминала без перезапуска.

**Ожидай:** пустой вывод.

### 1.1.3. Intel Mac — brew в PATH

Выполняется только на компьютерах Mac с процессорами Intel (`x86_64`). Компьютеры Apple Silicon этот шаг пропускают.

```bash
echo 'eval "$(/usr/local/bin/brew shellenv)"' >> ~/.zprofile
```

Прописываем пути Intel-версии Homebrew в автозагрузку.

**Ожидай:** пустой вывод.

```bash
eval "$(/usr/local/bin/brew shellenv)"
```

Активируем пути в текущем терминале.

**Ожидай:** пустой вывод.

### 1.1.4. Проверка Homebrew

```bash
brew --version
```

Проверяем доступность утилиты brew.

**Ожидай:** строку вида `Homebrew 4.x.x`. Если отображается `command not found` — вернитесь к шагу 1.1.2 (для M-чипов) или 1.1.3 (для Intel) и откройте новое окно терминала.

## 1.2. Docker & Docker Compose

Docker необходим для запуска локальной базы данных PostgreSQL 17 в изолированном контейнере.

### 1.2.1. macOS: Установка Docker через Homebrew

```bash
brew install --cask docker
```

Загружаем и устанавливаем официальное приложение Docker Desktop.

**Ожидай:** строку `docker was successfully installed!`. При сбое сети включите VPN и повторите.

### 1.2.2. macOS: Запуск приложения Docker

```bash
open -a Docker
```

Запускаем Docker Desktop в фоновом режиме.

**Ожидай:** пустой вывод. В строке меню macOS вверху экрана появится иконка кита. При первом старте Docker Desktop запросит подтверждение соглашения (кнопка «Accept») и системные привилегии администратора. Дождитесь, пока иконка кита перестанет мигать.

### 1.2.3. macOS: Проверка работы демона Docker

```bash
docker ps
```

**Ожидай:** заголовок таблицы с колонками `CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES`. Если терминал сообщает `Cannot connect to the Docker daemon` — Docker Desktop ещё загружается, подождите 10–15 секунд и повторите команду.

### 1.2.4. Linux и Ubuntu в WSL: Установка пакетов Docker Engine

В Ubuntu все действия выполняются внутри терминала дистрибутива:

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg git
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
. /etc/os-release
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu ${VERSION_CODENAME} stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

**Ожидай:** завершение установки пакетов без сообщений об ошибках. При таймауте загрузки ключа включите VPN.

### 1.2.5. Linux и Ubuntu в WSL: Права пользователя и служба Docker

```bash
sudo usermod -aG docker $USER
sudo service docker start || sudo systemctl start docker
```

Предоставляем пользователю права запуска контейнеров без префикса `sudo` и запускаем службу демона Docker.

**Ожидай:** сообщение `* Starting Docker: docker [ OK ]` или тихий старт службы.

### 1.2.6. Linux и Ubuntu в WSL: Проверка прав запуска контейнеров

Закройте окно терминала Ubuntu и откройте его заново (это необходимо для применения группы `docker`). В новом окне выполните:

```bash
docker ps
```

**Ожидай:** заголовок таблицы контейнеров без ошибки `permission denied`.

### 1.3.4. Linux (чистая система, не WSL)

```bash
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://packages.microsoft.com/keys/microsoft.asc | gpg --dearmor | sudo tee /etc/apt/keyrings/packages.microsoft.gpg > /dev/null
sudo chmod a+r /etc/apt/keyrings/packages.microsoft.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/packages.microsoft.gpg] https://packages.microsoft.com/repos/code stable main" | sudo tee /etc/apt/sources.list.d/vscode.list > /dev/null

```

В стандартных репозиториях Ubuntu пакета `code` нет, поэтому подключаем официальный apt-репозиторий Microsoft.

**Ожидай:** номер версии `1.xx.x`.

### 1.3.5. Windows (хост): установка VS Code и расширения WSL

Если WSL ещё не установлен, сначала откройте PowerShell **от имени Администратора** и выполните:

```powershell
wsl --install
```

Команда включает компоненты WSL и `VirtualMachinePlatform` и ставит Ubuntu. После установки перезагрузите компьютер и дождитесь первого запуска Ubuntu (там нужно создать имя пользователя и пароль).

Установите официальный дистрибутив VS Code для Windows с сайта [code.visualstudio.com](https://code.visualstudio.com) или выполните в PowerShell:

```powershell
winget install Microsoft.VisualStudioCode --source winget
```

Флаг `--source winget` надёжнее: установка идёт из основного репозитория winget, а не из Microsoft Store. Внутри Ubuntu в WSL сам пакет VS Code ставить не нужно.

Порядок действий для Windows:
1. Запустите VS Code в Windows.
2. Установите расширение **WSL**: нажмите `Ctrl+Shift+X`, введите `ms-vscode-remote.remote-wsl` и нажмите «Install».
3. Откройте палитру команд (`Ctrl+Shift+P`), введите `WSL: Connect to WSL` и нажмите Enter.
4. В левом нижнем углу окна VS Code появится зелёная плашка `WSL: Ubuntu`.

Проверка в терминале Ubuntu:

```bash
code --version
```

**Ожидай:** номер версии вида `1.xx.x`.

## 2.3. Защита `.env` от попадания в Git + первый коммит-чекпоинт

В репозитории `.env` может быть случайно зафиксирован или отслеживаться Git. Если вписать реальный API-ключ и затем сделать коммит или переключить ветку, секреты попадут в историю контроля версий или затрутся. Чиним это немедленно до внесения любых ключей.

### 2.3.1. Дописать .gitignore

```bash
grep -qxF '.env' ~/work/Python-AI/fastapi/.gitignore || printf "%s\n" '.env' '.env.*' '!.env.example' >> ~/work/Python-AI/fastapi/.gitignore
```

Говорим Git полностью игнорировать `.env` и его производные, но оставлять публичный шаблон `.env.example`.

**Ожидай:** пустой вывод.

### 2.3.2. Убрать .env из индекса Git

```bash
cd ~/work/Python-AI
git rm --cached -f fastapi/.env 2>/dev/null || true
```

Git перестаёт отслеживать файл `.env`, при этом сам файл на диске сохраняется.

**Ожидай:** вывод `rm 'fastapi/.env'` или тишина, если файл ранее не находился в индексе.

### 2.3.3. Настройка автора и первый коммит-чекпоинт

В свежем клоне `git commit` может завершиться ошибкой, если не указаны имя и почта автора. Зададим их для учебных коммитов:

```bash
cd ~/work/Python-AI
git config user.email "workshop@local"
git config user.name "Workshop Participant"
git add fastapi/.gitignore
git status --porcelain
```

**Ожидай:** строки `M fastapi/.gitignore` и/или `D fastapi/.env`. В выводе **не должно** быть строки `A fastapi/.env`.

Зафиксируем защиту секретов в ветке:

```bash
git commit -m "chore: перестать трекать .env"
```

**Ожидай:** строку `chore: перестать трекать .env` и количество изменённых файлов (или `nothing to commit`, если защита уже была зафиксирована ранее).

### 2.3.4. Проверка: Git больше не видит .env

```bash
cd ~/work/Python-AI
git check-ignore -v fastapi/.env
```

Подтверждаем, что файл надёжно исключён из системы контроля версий.

**Ожидай:** строку с указанием правила `.gitignore` и пути к файлу.

## 2.4. Python-окружение (uv + virtualenv)

На интенсиве используется молниеносный пакетный менеджер **uv** от Astral. Он автоматически загружает изолированную версию Python 3.14 и разворачивает виртуальное окружение `.venv` за несколько секунд.

### 2.4.1. Установка uv

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
grep -Fq '.local/bin' ~/.zprofile 2>/dev/null || echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zprofile
grep -Fq '.local/bin' ~/.bashrc 2>/dev/null || echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
uv --version
```

**Ожидай:** версию вида `uv 0.x.x` (или `uv 1.x.x`).

### 2.4.2. Установка зависимостей проекта (uv sync)

```bash
cd ~/work/Python-AI/fastapi
uv sync --python 3.14
```

Флаг `--python 3.14` обязателен: без него uv может скачать более свежий Python 3.15, а бинарные wheels `psycopg-binary` 3.3.4 собраны строго под Python 3.14 (под 3.15 их нет, и установка падает). Команда скачивает интерпретатор Python 3.14, создает локальное виртуальное окружение `.venv` и устанавливает все зависимости из lock-файла (FastAPI, SQLAlchemy 2.0, psycopg, Alembic, pytest, ruff, basedpyright).

**Ожидай:** строки `Resolved ... packages` и `Installed ... packages` без сообщений об ошибках.

### 2.4.3. Проверка каталога .venv

```bash
ls ~/work/Python-AI/fastapi/.venv
```

**Ожидай:** наличие каталогов `bin` (на macOS/Linux) и `lib`.

## 2.7. Запуск локальной базы данных PostgreSQL 17 в Docker

Сервис сокращения ссылок требует работающей реляционной СУБД с поддержкой драйвера `psycopg`.

### 2.7.1. Запуск контейнера db

```bash
cd ~/work/Python-AI/fastapi
docker compose down -v 2>/dev/null || true
docker compose up -d --wait db
```

Сначала `docker compose down -v` удаляет старые контейнеры и тома (если они остались от прошлых запусков): так база стартует с чистой схемы, и начальная миграция Alembic применится без конфликтов. Затем запускаем контейнер базы данных в фоновом режиме с флагом `--wait` (команда ждет, пока база пройдет проверку работоспособности healthcheck).

**Ожидай:** строки `Container ... Created`, `Container ... Started` и `Healthy`.

### 2.7.2. Проверка доступности порта 5432 и статуса контейнера

```bash
docker compose ps db
```

**Ожидай:** статус контейнера `Up ... (healthy)` и проброшенный порт `0.0.0.0:5432->5432/tcp`.

### 2.7.3. Применение начальных миграций Alembic

Создаем таблицы в базе данных по готовым миграциям проекта:

```bash
cd ~/work/Python-AI/fastapi
uv run alembic upgrade head
```

**Ожидай:** строку `Running upgrade  -> 0001_create_links, create links table` без ошибок подключения.

### 2.7.4. Проверка текущей ревизии схемы

```bash
cd ~/work/Python-AI/fastapi
uv run alembic current
```

**Ожидай:** строку с идентификатором ревизии и пометкой `(head)`. База данных готова к работе сервиса.
